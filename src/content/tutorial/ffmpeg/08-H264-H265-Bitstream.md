I、P、B 不是三种画质，也不是三种文件格式。它们描述的是：**编码器准备了哪些数据，让解码器还原出这一幅画面。**

读这篇时先抓住一条线：

```text
摄像头得到原始画面
        ↓
编码器把画面写成压缩数据
        ↓
解码器读取压缩数据，重建完整画面
        ↓
播放器按时间显示画面
```

本文只解释这条线上的画面压缩。H.264、MP4、RTSP 和 RTP 各自处在哪一层，留到后两篇再讲。

## 先分清三样东西

屏幕最后显示的是一幅完整画面，但文件或网络里通常没有逐幅保存所有像素。中间至少要区分三样东西：

| 名称 | 它是什么 | 在哪里出现 |
| --- | --- | --- |
| 原始画面 | 摄像头或程序得到的像素 | 编码之前 |
| 编码数据 | 用来重建画面的压缩数据 | 文件、码流或网络负载中 |
| 解码画面 | 解码器根据编码数据还原出的像素 | 播放、Filter、截图之前 |

一帧（Frame）通常指某个时间点的一幅画面。25 FPS 表示一秒安排 25 幅画面，相邻画面的显示时间通常相差 40 毫秒。

```text
显示时间     0 ms       40 ms      80 ms      120 ms
画面       [●···]     [·●··]     [··●·]     [···●]
```

每一幅解码画面都是完整的。所谓 P 帧“只保存变化”是一种方便记忆的说法，但不够准确：编码数据里还要写参考位置、预测方式和预测不准的部分，解码器才能得到完整画面。

## 为什么不把每幅画面原样保存

门口的监控画面连续拍了四次。墙、地面和门框基本没变，只有一个人向前走。若每次都把整幅画面的所有像素重新写一遍，大量数据会重复。

编码器会把画面分块，寻找可以重复利用的图像信息：

```text
上一幅已重建画面： [··●·····]
当前原始画面：     [···●····]

编码器发现：当前的小球很像参考画面里的小球，只是位置变了。
```

它据此算出一幅近似画面，这一步叫预测（Prediction）。近似画面通常还不够准确，所以还要记录差别，也就是残差（Residual）。

```text
预测值             100
当前原始值         107
残差               107 - 100 = 7

解码时：预测值 + 还原后的残差 = 重建值
```

真实编码按图像块处理，并且还会经过变换、量化等步骤。量化会舍弃一部分精度，因此解码结果可能接近原始画面，却不逐像素相同。这里先不用记算法名称，只要知道：

```text
参考画面提供可复用的部分
残差补上预测不准的部分
两者合起来，得到当前的解码画面
```

## I、P、B 的区别就在“参考谁”

现在再看三个名字：

| 常见称呼 | 怎样得到当前画面 | 初学时可以先记成 |
| --- | --- | --- |
| I 帧（Intra-coded picture） | 只使用当前画面内部已经还原的邻近像素进行预测，不使用其他画面作帧间参考 | 自己完成重建 |
| P 帧（Predictive-coded picture） | 可以使用已经重建的其他画面作参考，再结合当前数据重建 | 借已知画面预测 |
| B 帧（Bi-predictive-coded picture） | 可以组合两个参考结果，也可以只使用一个参考，再结合当前数据重建 | 可从更多方向找参考 |

这里有三个容易误解的地方：

- I 帧仍是压缩数据，不是一张未压缩图片。
- P 帧和 B 帧解码后也是完整画面，不是只能显示一部分。
- P/B 画面内部仍可以有不依赖其他画面的块；字母描述的是允许使用的编码方式，不是每个像素都必须采用同一种方式。

## 为什么 B 帧会改变解码顺序

假设三幅画面的显示顺序是 `I0 → B1 → P2`。如果 B1 要参考 I0 和 P2，解码器必须先得到 P2，才能重建 B1。

```text
观众看到的顺序： I0 → B1 → P2
解码器工作的顺序：I0 → P2 → B1
```

所谓 B 帧参考“后面的画面”，这个“后面”指显示时间更晚。真正解码 B1 时，P2 已经先被送到解码器并完成重建。

</video-coding-demo>

因此媒体中常见两种时间：

- PTS（Presentation Time Stamp）：这份内容什么时候显示；
- DTS（Decoding Time Stamp）：这份内容什么时候送去解码。

没有画面重排时，两者可能相同；存在重排时，它们可能不同。关闭 B 帧可以减少这一类等待，但直播总延迟还包括采集、编码、网络、缓冲和显示，不能只看 B 帧。

## 码流究竟是什么

编码器要把预测方式、参考信息、残差和解码配置写成连续的二进制数据。这串按编码规范组织的数据，就是编码码流（bitstream）。

可以把几个常见对象按顺序放在一起：

```text
原始 Frame
   ↓ Encode
Packet（携带一段 H.264 / H.265 编码数据）
   ↓ 写入容器，或者按传输协议分包
MP4 / MKV 文件，或者 RTP 等实时媒体数据
   ↓ 从容器取出，或者从网络分片重组
Packet
   ↓ Decode
解码后的 Frame
```

这里的箭头只说明处理关系，不表示它们一一对应：

- 一幅画面的编码数据可能由多个编码单元组成；
- 一个网络包可能只装其中一小片；
- FFmpeg 的一个 Packet 也不能简单等同于一个 RTP 网络包；
- MP4 是组织音视频和时间信息的容器，不是视频编码。

下一篇会继续打开 H.264/H.265 码流，解释 NAL、参数集、裸码流与 MP4。当前只要把“码流”理解成**解码器可以按某种编码规则读取的压缩数据**。

## 为什么中途打开直播会先黑一会儿

假设播放器刚连上时，最先收到的是 P 帧。P 帧需要参考画面，但那些参考画面已经在连接之前发完了。当前数据即使完整，解码器也可能缺少重建依据。

```text
发送端： I ─ P ─ P ─ P ─ I ─ P ...
                    ↑
                 此时接入

接收端没有左边已经发完的参考，通常要等新的可用入口。
```

这时会遇到三个常见名称：

| 名称 | 先怎样理解 |
| --- | --- |
| GOP（Group of Pictures） | 一组连续画面的编码组织；具体参考关系由编码器决定 |
| 关键帧（Keyframe） | 文件或工具标记的可访问入口，确切含义要结合编码格式 |
| IDR | H.264/H.265 中一种明确的刷新点；后续画面不再引用 IDR 之前的参考画面 |

I 帧只说明当前画面采用帧内编码，IDR 还约束后续参考关系。因此“看到 I 帧”与“已经获得可靠的中途起播条件”不能无条件画等号。解码器通常还需要有效的参数配置，新的刷新画面也必须完整到达。

如果设备每 2 秒提供一次可用刷新点，新观众恰好错过一次，就可能等待接近 2 秒。缩短间隔有利于起播和错误恢复，但可能增加数据量或降低同码率下的压缩效率。

## 用 FFmpeg 亲眼看一次

下面生成 3 秒、25 FPS 的测试视频。先确认当前 FFmpeg 构建有 `libx264`：

```powershell
ffmpeg -hide_banner -encoders 2>&1 | Select-String "libx264"
```

在空目录中运行：

```powershell
ffmpeg -n -hide_banner -f lavfi -i "testsrc2=size=320x180:rate=25" -t 3 -an -c:v libx264 -pix_fmt yuv420p -g 25 -bf 2 -x264-params "keyint=25:min-keyint=25:scenecut=0:open-gop=0:b-adapt=0" frames-demo.mp4
```

这条命令故意固定了一些编码选择，方便观察，不代表生产配置。`-g 25` 把最大关键帧间隔设为 25，`-bf 2` 允许最多两个连续 B 帧。

先看解码后的画面类型：

```powershell
ffprobe -v error -select_streams v:0 -show_frames -show_entries frame=best_effort_timestamp_time,pict_type,key_frame -of json frames-demo.mp4
```

输出中：

- `pict_type` 是 I、P 或 B；
- `best_effort_timestamp_time` 是解码器估计的显示时间；
- `key_frame` 是 FFmpeg 给出的关键帧标志。

再看压缩 Packet 的显示时间和解码时间：

```powershell
ffprobe -v error -select_streams v:0 -show_packets -show_entries packet=pts_time,dts_time,size,flags -of json frames-demo.mp4
```

带 B 帧的样本中可以观察到 PTS 与 DTS 的差异。开头出现负 DTS 可能是重排时间的表达，不能仅凭这一点判断文件损坏。

最后完整解码并播放：

```powershell
ffmpeg -v error -i frames-demo.mp4 -map 0:v:0 -f null -
ffplay frames-demo.mp4
```

## 离开这篇前，只检查四件事

1. 播放器最后显示的 I/P/B 都是完整画面。
2. P/B 的编码数据可以利用其他已重建画面，但仍要携带预测方式和残差等信息。
3. B 帧可能让解码顺序和显示顺序不同。
4. 码流是按编码规范组织的压缩数据；它不是 MP4，也不是 RTP 网络包。

如果这四点已经清楚，就可以继续看[H.264、H.265、MP4 和 GB 分别是什么](/tutorials/tffmpeg-codecs/)。NAL、SPS/PPS/VPS、Annex B 都放在那里，不需要在本篇提前记。
