这是一篇总纲。学习 FFmpeg 的目标不是记住大量参数，而是能把一个媒体任务拆成输入、流选择、处理方式和输出约束，再用工具验证结果。

## 一张图理解 FFmpeg

```mermaid
flowchart LR
  A[输入文件 / 网络流 / 设备] --> B[Demux 解封装]
  B --> C{处理方式}
  C -->|不改内容| D[Stream Copy]
  C -->|需要修改| E[Decode 解码]
  E --> F[Filter 滤镜]
  F --> G[Encode 编码]
  D --> H[Mux 封装]
  G --> H
  H --> I[输出文件 / 推流地址]
```

选择 `Stream Copy` 还是“解码 → 滤镜 → 编码”，是大多数 FFmpeg 命令最重要的分界。

## 核心知识地图

| 主题 | 必须理解的内容 | 常用工具或参数 |
| --- | --- | --- |
| 媒体模型 | 容器、编码、Stream、Packet、Frame | `ffprobe` |
| 处理链路 | Demux、Decode、Filter、Encode、Mux | `-c copy`、`-vf`、`-af` |
| 流选择 | 自动选择、手动映射、可选映射、负映射 | `-map`、`-vn`、`-an` |
| 时间 | time base、PTS/DTS、帧率、采样率、时长 | `-ss`、`-t`、`fps` |
| 质量与体积 | 有损/无损、CRF、码率、preset | `-crf`、`-b:v`、`-preset` |
| 兼容性 | 编码、像素格式、采样格式与容器/播放器能力 | `-pix_fmt`、`-movflags` |
| 实时流 | 协议、超时、延迟、重连、持续验证 | `-rtsp_transport`、`-f null` |
| 自动化 | 可重复、可观察、可验证、安全覆盖 | `-nostdin`、`-progress`、`ffprobe` |

第一阶段先掌握前五项。硬件加速、复杂时间戳和实时流优化应建立在可验证的软件编码流程之上。

## 如何阅读一条命令

FFmpeg 的基本语法是：

```text
ffmpeg [全局参数] {[输入参数] -i 输入} ... {[输出参数] 输出} ...
```

例如：

```powershell
ffmpeg -hide_banner -ss 00:00:05 -i input.mp4 -map 0:v:0 -map 0:a:0? -t 10 -c:v libx264 -crf 23 -c:a aac output.mp4
```

按作用域拆开后并不复杂：

| 片段 | 含义 |
| --- | --- |
| `-hide_banner` | 全局参数，精简启动日志 |
| `-ss 00:00:05` | 输入参数，从输入约第 5 秒开始定位 |
| `-i input.mp4` | 第 0 个输入 |
| `-map 0:v:0` | 选择第 0 个输入的第一条视频流 |
| `-map 0:a:0?` | 音频存在就选择，不存在也不报错 |
| `-t 10` | 输出约 10 秒 |
| `-c:v libx264 -crf 23` | 视频使用 H.264 软件编码并设置恒定质量 |
| `-c:a aac` | 音频编码为 AAC |
| `output.mp4` | 当前输出 URL |

参数通常作用于它后面的下一个输入或输出，遇到多输入、多输出时必须按文件边界重新阅读。

## 如何从需求编写命令

### 1. 先探测，不猜输入

```powershell
ffprobe -v error -show_format -show_streams -of json input.mp4
```

至少确认：

- 有哪些视频、音频、字幕流；
- 编码和像素格式是什么；
- 分辨率、帧率、采样率、声道数是多少；
- 时长是否可信，输入是否存在异常时间戳。

### 2. 把目标写成约束

不要只写“压缩视频”，而要写成可验证目标，例如：

```text
保留第一条视频和可选的第一条音频；
输出 MP4；视频编码 H.264、最长边不超过 1280；
音频 AAC 128 kbit/s；文件适合网页渐进播放。
```

### 3. 明确选择哪些流

单音视频文件可以依赖自动选择，但工程脚本建议显式 `-map`：

```powershell
ffmpeg -i input.mp4 -map 0:v:0 -map 0:a:0? ... output.mp4
```

问号表示该流可选，适合兼容“有些输入没有音频”的批处理。

### 4. 决定复制还是转码

如果不改变编码内容，且目标容器支持原编码，可尝试：

```powershell
ffmpeg -i input.mkv -map 0 -c copy output.mkv
```

只要需要缩放、加水印、改变帧率、烧录字幕或改变编码，就必须解码并重新编码相应流。

### 5. 写输出参数

```powershell
ffmpeg -i input.mp4 -map 0:v:0 -map 0:a:0? -vf "scale=w=1280:h=-2:force_original_aspect_ratio=decrease" -c:v libx264 -crf 23 -preset medium -pix_fmt yuv420p -c:a aac -b:a 128k -movflags +faststart output.mp4
```

这里的参数来自目标约束，不是固定模板。比如归档场景未必需要 `yuv420p`，直播场景也不会只靠 `+faststart` 解决延迟。

### 6. 验证输出

```powershell
ffprobe -v error -show_entries format=duration,size,format_name -show_entries stream=index,codec_type,codec_name,width,height,pix_fmt,avg_frame_rate,sample_rate,channels -of json output.mp4
```

还应实际播放，检查开头、结尾、音画同步、方向、色彩和目标播放器兼容性。

## 常见需求模板

| 需求 | 是否重编码 | 核心写法 |
| --- | --- | --- |
| 只换容器 | 通常否 | `-map 0 -c copy` |
| 改编码或压缩 | 是 | `-c:v libx264 -crf 23` |
| 缩放、裁剪、水印 | 对应流必须 | `-vf` 或 `-filter_complex` |
| 替换音频 | 视频可复制，音频视格式决定 | 两个 `-i` 配合 `-map` |
| 快速切片 | 可不重编码，但切点受关键帧影响 | 输入前 `-ss`、`-c copy` |
| 精确切片 | 是 | 解码后输出指定时长 |
| RTSP 连通性验证 | 不必保存 | `-rtsp_transport tcp`、`-f null -` |
| 程序读取媒体信息 | 否 | `ffprobe -of json` |

## 编写工程脚本时的底线

1. **固定并记录版本**：不同构建的编码器和默认行为可能不同。
2. **不拼接不可信参数**：文件名、滤镜表达式和网络地址要作为受控参数处理。
3. **设置资源边界**：限制运行时长、输出目录、磁盘占用和并发数。
4. **保留退出码与 stderr**：不要只搜索一行错误文本，也不要把进度日志全部当成故障。
5. **敏感信息脱敏**：RTSP URL、HTTP Header 和命令行可能泄露凭据。
6. **写后验证**：对输出做结构探测；关键业务还要做解码或播放验收。
7. **硬件加速要有回退**：显卡、驱动、FFmpeg 构建和像素格式必须同时兼容。

## 容易形成的错误观念

| 错误观念 | 正确认识 |
| --- | --- |
| 改扩展名就是格式转换 | 扩展名不能改变容器结构或编码内容 |
| `-c copy` 会降低画质 | 它复制压缩 Packet，不重新编码；但可能与目标容器不兼容 |
| CRF 是百分比画质 | CRF 是编码器相关的质量控制值，不能跨编码器直接比较 |
| 码率越高一定越清晰 | 还取决于编码器、内容复杂度、分辨率、帧率和编码设置 |
| `-r` 放哪里都一样 | 输入和输出位置语义不同；普通文件改帧率更推荐 `fps` 滤镜明确生成帧 |
| FFmpeg 退出码为 0 就完成验收 | 还要核对结构、可解码性、播放兼容与业务目标 |
| RTSP 打不开就是编码问题 | 网络、鉴权、URL、设备状态和传输方式都可能是原因 |

## 推荐练习顺序

1. 生成 `sample.mp4`，用 `ffprobe` 找出每条 Stream。
2. 转封装并比较前后 `codec_name`，确认没有重编码。
3. 使用 CRF 转码，比较耗时、体积和画质。
4. 缩放、截图、抽帧，观察滤镜为什么会触发重编码。
5. 生成第二段音频并用 `-map` 替换原音频。
6. 分别做快速切片和精确切片，观察关键帧与时长差异。
7. 对真实 RTSP 做限时读取，并按网络、鉴权、地址、数据四层定位失败。

完成这些练习后，再进入复杂 Filtergraph、HLS、硬件加速与生产级实时流，会更容易判断问题发生在哪一层。
