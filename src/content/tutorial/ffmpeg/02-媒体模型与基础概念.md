很多 FFmpeg 问题不是参数不会用，而是把容器、编码和数据流当成同一件事。先建立媒体模型，后续命令会简单很多。

## 容器、编码与 Stream

```text
sample.mp4                         ← 容器
├── Stream #0:0: H.264 Video       ← 一条压缩视频流
├── Stream #0:1: AAC Audio         ← 一条压缩音频流
└── metadata / chapters            ← 元数据或章节
```

| 概念 | 回答的问题 | 示例 |
| --- | --- | --- |
| 容器（Format） | 多条数据如何组织、索引和保存 | MP4、Matroska、MPEG-TS |
| 编码（Codec） | 视频或音频如何压缩表示 | H.264、H.265、AV1、AAC、Opus |
| Stream | 容器中的一条连续媒体数据 | 第一路视频、第二路音频、字幕 |

`.mp4` 表示容器，不等于 H.264；MP4 中也可能放 H.265、AV1 或其他受支持的编码。反过来，同一条 H.264 视频也能被封装在 MP4、MKV 或 MPEG-TS 中。

只改文件扩展名不会修改容器结构：

```powershell
Rename-Item input.mkv output.mp4
```

这不是格式转换。正确做法至少要让 FFmpeg 重新封装：

```powershell
ffmpeg -i input.mkv -map 0 -c copy output.mp4
```

这条命令仍可能因为目标 MP4 不支持某条输入流而失败，失败时应根据实际 Stream 决定丢弃、转换或改用其他容器。

## Packet 与 Frame

压缩后的数据通常以 Packet 在解复用器、解码器、编码器和复用器之间流动；解码后的原始数据称为 Frame。

```mermaid
flowchart LR
  A[容器中的压缩数据] --> B[Packet]
  B --> C[Decoder]
  C --> D[原始 Frame]
  D --> E[Filter]
  E --> F[Encoder]
  F --> G[新 Packet]
```

对视频来说，Frame 是一幅解码后的图像；对音频来说，Frame 是一批音频采样。不要把“视频的一帧”和“网络协议的一包”混为一谈。

Stream Copy 直接传递 Packet：

```text
Packet → Muxer
```

因此它很快、不会产生二次有损编码，但也不能缩放、加水印或改变画面内容。

## 视频的关键属性

| 属性 | 含义 | 常见误区 |
| --- | --- | --- |
| 分辨率 | 每帧像素宽高，如 1920×1080 | 分辨率高不保证画质高 |
| 帧率 | 每秒呈现的帧数或帧时间分布 | `r_frame_rate` 不一定等于实际平均帧率 |
| 像素格式 | 像素如何存储，如 `yuv420p` | 编码器支持不等于播放器支持 |
| 码率 | 单位时间的压缩数据量 | 高码率不一定来自高质量源 |
| 色彩信息 | 色彩空间、范围、传递特性等 | 丢失或误标会导致偏色、发灰 |

查看视频流：

```powershell
ffprobe -v error -select_streams v:0 -show_entries stream=codec_name,profile,width,height,pix_fmt,r_frame_rate,avg_frame_rate,color_space,color_transfer,color_primaries -of json input.mp4
```

帧率最好用分数保留，例如 `30000/1001`，不要在程序里过早四舍五入成 `29` 或 `30`。

## 音频的关键属性

| 属性 | 含义 | 示例 |
| --- | --- | --- |
| 采样率 | 每秒采样次数 | 44100 Hz、48000 Hz |
| 声道数 | 同时存在的音频通道数量 | 1、2、6 |
| 声道布局 | 每个声道代表的位置 | mono、stereo、5.1 |
| 采样格式 | 单个采样值的表示方式 | `fltp`、`s16` |
| 码率 | 压缩音频每秒的数据量 | 128 kbit/s、256 kbit/s |

查看第一条音频流：

```powershell
ffprobe -v error -select_streams a:0 -show_entries stream=codec_name,sample_rate,channels,channel_layout,sample_fmt,bit_rate -of json input.mp4
```

## Stream 编号怎么读

日志中的 `Stream #0:1` 表示：

```text
0 → 第一个输入
1 → 该输入中全局索引为 1 的 Stream
```

而 `0:a:1` 表示：

```text
0 → 第一个输入
a → 音频类型
1 → 匹配到的第二条音频 Stream
```

两种编号不是同一个维度。先用 `ffprobe` 查看 `index` 与 `codec_type`，再写 `-map`，不要根据常见的 `0:0` 视频、`0:1` 音频排列进行猜测。

## 时间基、PTS 与 DTS

媒体时间不是只靠“第几帧”表达。每条 Stream 都有 time base，时间戳数值乘以 time base 才得到秒数。

```text
实际时间 = 时间戳 × time_base
```

| 字段 | 作用 |
| --- | --- |
| PTS | 该帧应在何时呈现 |
| DTS | 该压缩数据应在何时送入解码器 |
| duration | Stream 或 Packet 持续时间 |
| start_time | 媒体时间轴的起点 |

存在 B 帧时，解码顺序与显示顺序可能不同，所以 PTS 和 DTS 不必相等。对网络流或损坏文件，时间戳不连续可能表现为卡顿、音画不同步或非单调 DTS 错误。

查看容器与 Stream 时间信息：

```powershell
ffprobe -v error -show_entries format=start_time,duration -show_entries stream=index,codec_type,time_base,start_time,duration -of json input.mp4
```

不要把 `N/A` 时长直接当成损坏。实时流、某些管道和没有完整索引的输入本来就可能无法预先得到总时长。

## 帧率不只是一个数字

固定帧率（CFR）通常让相邻视频帧间隔一致；可变帧率（VFR）的帧间隔可以变化。FFmpeg 为不同目的暴露多个字段：

- `r_frame_rate` 常用于表示可表达的基础帧率或流速率，不保证等于实际平均输出；
- `avg_frame_rate` 是平均帧率，仍可能因输入不完整而不可靠；
- 对严格分析，应检查 Packet/Frame 时间戳，而不是只读一个 FPS 字段。

查看前若干视频帧时间戳：

```powershell
ffprobe -v error -select_streams v:0 -show_entries frame=best_effort_timestamp_time,pkt_duration_time,key_frame -of csv input.mp4
```

## 关键帧与随机访问

有损视频通常不是每帧都能独立解码。关键帧提供随机访问入口，其他帧可能依赖前后参考帧。

这会直接影响：

- `-c copy` 快速切片的起点精度；
- 播放器拖动和首帧速度；
- HLS 分片边界；
- 丢包后的恢复时间。

列出关键帧时间：

```powershell
ffprobe -v error -select_streams v:0 -skip_frame nokey -show_entries frame=pts_time -of csv=p=0 input.mp4
```

## 用 ffprobe 建立事实

面向人工阅读：

```powershell
ffprobe -hide_banner input.mp4
```

面向程序读取：

```powershell
ffprobe -v error -show_format -show_streams -of json input.mp4
```

如果需要判断文件是否能完整解码，仅看元数据还不够，可以把解码结果丢弃：

```powershell
ffmpeg -v error -i input.mp4 -map 0:v:0 -map 0:a:0? -f null -
```

这个检查会消耗解码时间，但能发现许多只读容器头无法发现的数据错误。
